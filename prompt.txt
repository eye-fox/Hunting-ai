## PHASE 1: CONTEXT UNDERSTANDING

1. **Pahami Repo Tanpa Prasangka**:

   A. Git clone repo, Baca README.md, package.json, dan dokumentasi:
      - Apa masalah yang diselesaikan aplikasi ini?
      - Siapa target pengguna?
      - Fitur apa yang paling penting?
      - Bagaimana arsitekturnya?
      - Catat semua informasi penting

   B. Pelajari struktur dan alur:
      - Pahami struktur dengan menjalankan tools "python pohon.py <direktori>" untuk melihat struktur pohon dari target
      - Buat peta: "File ini untuk apa? Hubungannya dengan file lain?"
      - Identifikasi file yang paling sering diakses/diubah
      - Cari file yang JARANG diubah - biasanya mengandung bug tersembunyi
      - Cari file yang baru diubah - bisa mengandung regression

   C. Temukan "Pola Pikir Developer":
      - Bagaimana mereka menulis kode? (gaya, konsistensi)
      - Apa yang mereka asumsikan? (cari komentar "assuming that...", "should be...")
      - Dimana mereka paling percaya diri? (biasanya di situlah celahnya)

   D. Identifikasi High-Value Targets:
      - Fitur yang berhubungan dengan uang/data sensitif
      - Authentication & Authorization
      - File operations (upload, download, delete)
      - External API calls / Webhooks
      - Admin panel / Dashboard
      - User management

## PHASE 2: ANOMALY DETECTION

2. **Cari Segala Hal yang "Tidak Wajar"**:

   A. **Pola yang Tidak Konsisten**:
      - Fungsi A menggunakan auth, fungsi B di file yang sama TIDAK
      - Validasi di satu tempat, tapi tidak di tempat lain
      - Error handling berbeda untuk situasi yang sama
      - Naming convention berubah di tengah jalan
      - Satu file sangat panjang (1000+ baris) - tanda "god object"
      - Satu fungsi melakukan terlalu banyak hal - single responsibility violation

   B. **Kode yang Terlalu "Pintar"**:
      - Kode yang sulit dipahami (over-engineering) - biasanya mengandung bug
      - Reflection, dynamic dispatch, eval - sulit dilacak
      - Metaprogramming - sulit dianalisis secara statis
      - Code generation - cek generated code, sering bermasalah

   C. **Kode yang Terlalu "Sederhana"**:
      - Tidak ada error handling
      - Tidak ada validasi
      - Tidak ada logging
      - Tidak ada rate limiting
      - Tidak ada timeout

   D. **Konfigurasi yang Mencurigakan**:
      - Debug mode aktif
      - CORS: *
      - Allow all hosts
      - Default credentials
      - Hardcoded values (terutama untuk production)
      - Environment variable yang tidak digunakan

## PHASE 3: BEHAVIORAL ANALYSIS

3. **Analisis Perilaku Sistem (Tanpa Melihat Tipe Bug)**:

   Untuk setiap fungsi/endpoint penting, tanyakan:

   A. **INPUT → PROSES → OUTPUT**:
      - Input apa yang diterima?
      - Bagaimana input diproses?
      - Output apa yang dihasilkan?
      - APA YANG TERJADI JIKA INPUT BERBEDA DARI YANG DIHARAPKAN?

   B. **DEPENDENSI**:
      - Fungsi ini bergantung pada apa?
      - Apa yang terjadi jika dependency gagal?
      - Apa yang terjadi jika dependency memberikan hasil yang tidak diharapkan?

   C. **STATE**:
      - Apa state yang diperlukan sebelum fungsi ini dipanggil?
      - Apa yang terjadi jika fungsi dipanggil dengan state yang salah?
      - Apa yang terjadi jika fungsi dipanggil dua kali?
      - Apa yang terjadi jika fungsi dipanggil dengan urutan yang salah?

   D. **SIDE EFFECTS**:
      - Apa efek samping dari fungsi ini?
      - Apa yang terjadi jika efek samping gagal?
      - Apa yang terjadi jika efek samping dipicu tanpa otorisasi?

   E. **TIMING**:
      - Berapa lama fungsi ini berjalan?
      - Apa yang terjadi jika dipanggil secara bersamaan?
      - Apa yang terjadi jika dipanggil sangat cepat?

   F. **AUTHENTICATION & AUTHORIZATION**:
      - Siapa yang bisa memanggil fungsi ini?
      - Bagaimana sistem tahu siapa pemanggilnya?
      - Apa yang terjadi jika session/token dimanipulasi?

## PHASE 4: EDGE CASE DETECTION

4. **Cari Kasus di Luar Ekspektasi Developer**:

   Untuk setiap operasi, pikirkan "Apa yang tidak dipikirkan developer?"

   A. **Matematika**:
      - Pembagian dengan nol
      - Overflow/underflow
      - Bilangan negatif di mana seharusnya positif
      - Bilangan sangat besar
      - NaN, Infinity
      - Floating point precision

   B. **String**:
      - String kosong
      - Spasi (leading/trailing/multiple)
      - Newline, tab, special characters
      - Unicode (emoji, non-ASCII, RTL)
      - Null byte (%00)
      - String sangat panjang
      - String dengan format yang tidak valid

   C. **Array/Collection**:
      - Array kosong
      - Array dengan elemen tidak terduga tipenya
      - Array yang sangat besar
      - Nested array yang dalam

   D. **Object/Dictionary**:
      - Object kosong
      - Object dengan field tidak dikenal
      - Object dengan field wajib tapi tidak ada
      - Object dengan circular reference

   E. **Waktu**:
      - Tanggal invalid
      - Timestamp negatif, 0, sangat besar
      - Waktu di masa lalu/masa depan ekstrim

   F. **File**:
      - File kosong
      - File sangat besar
      - File dengan nama tidak valid
      - File dengan path traversal (../)

## PHASE 5: LOGIC INVERSION

5. **Balik Logika Developer**:

   Developer biasanya memikirkan:
   - "Jika A terjadi, maka lakukan B"
   - "Jika user valid, maka berikan akses"

   Kita pikirkan sebaliknya:
   - "Apa yang terjadi jika A TIDAK terjadi, tapi B tetap terjadi?"
   - "Apa yang terjadi jika user TIDAK valid, tapi tetap mendapat akses?"

   Teknik:
   A. **Condition Inversion**:
      - `if (user.isAdmin())` → apa yang terjadi jika `!user.isAdmin()`?
      - `if (token.valid())` → apa yang terjadi jika token invalid?

   B. **Order Inversion**:
      - "Validasi dulu, baru proses" → apa jika proses dulu, validasi terakhir?
      - "Check auth dulu, baru akses resource" → apa jika akses resource dulu?

   C. **Expectation Inversion**:
      - Developer expects `x` → apa jika yang datang `y`?
      - Developer expects `valid` → apa jika yang datang `invalid`?

## PHASE 6: SYSTEM-LEVEL ANALYSIS

6. **Lihat Sistem Secara Keseluruhan**:

   A. **Data Flow Between Components**:
      - Bagaimana data mengalir dari A ke B ke C?
      - Dimana validasi terjadi? Di semua titik?
      - Apakah data yang sama diperlakukan berbeda di komponen berbeda?

   B. **Trust Boundaries**:
      - Dimana batas antara "trusted" dan "untrusted"?
      - Apakah ada titik di mana data untrusted masuk ke trusted zone tanpa validasi?

   C. **Single Point of Failure**:
      - Komponen apa yang paling kritis?
      - Apa yang terjadi jika komponen itu gagal?

   D. **Hidden Features**:
      - Ada endpoint/feature yang tidak terdokumentasi?
      - Ada debug mode/admin mode yang tersembunyi?

## PHASE 7: HYPOTHESIS GENERATION

7. **Buat Hipotesis Serangan TANPA MELIHAT TIPE BUG**:

   Berdasarkan analisis di atas, buat daftar "What if..." scenarios:

   Contoh hipotesis:
   - "What if I send a request that causes the system to enter an invalid state?"
   - "What if I trigger function A and function B simultaneously?"
   - "What if I send data that passes validation but breaks downstream processing?"
   - "What if I access resource X through endpoint Y instead of endpoint Z?"
   - "What if I complete step 3 without doing step 1 and 2?"
   - "What if I send 10,000 requests in 1 second?"
   - "What if I manipulate the state stored in the client?"
   - "What if I call a function with parameters from another function's context?"

   Prioritaskan hipotesis yang:
   - Paling tidak terduga
   - Paling berdampak
   - Paling mudah dieksekusi
   - Paling mungkin terjadi di real world

## PHASE 8: VALIDATION PROTOCOL

8. **Validasi Tanpa Mengetahui Nama Bug**:

   Untuk setiap hipotesis:

   A. **Static Validation**:
      - Trace kode: apakah hipotesis mungkin terjadi?
      - Cek semua validasi di path eksekusi
      - Cek apakah ada guard/mitigasi
      - Cek apakah ada test case yang mencakup skenario ini

   B. **Dynamic Validation (jika bisa)**:
      - Buat request sesuai hipotesis
      - Amati response, error, behavior
      - Cek apakah ada side effect yang tidak diinginkan

   C. **Impact Assessment**:
      - Jelaskan konsekuensi:
        * "Ini menyebabkan [behavior tidak terduga]"
        * "Ini memungkinkan [action yang seharusnya tidak mungkin]"
        * "Ini menghasilkan [informasi/akses yang seharusnya private]"
        * "Ini menyebabkan [konsekuensi bisnis]"

   D. **Verification**:
      - Apakah behavior ini by design?
      - Apakah ada dokumentasi yang menjelaskan?
      - Apakah ada konfigurasi untuk mengaktifkan/menonaktifkan?
